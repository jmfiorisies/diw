    1. Por qué "funciona en mi máquina" no es suficiente 

    flowchart TD
    A["Desarrollo local en<br/>Chrome + macOS"] --> B{"¿Se comporta igual en...?"}

    Cada navegador implementa los estándares web a diferentes ritmos y con matices propios en sus motores de renderizado. Por este motivo, el uso de características modernas (Container Queries en UD4 o formatos como AVIF en UD6) requiere estrategias de verificación cross-browser.

    Panel Utilidad principal Conexión con unidades previas

    Network Inspección de peticiones HTTP, tamaños de transferencia y tiempos. Verificación de carga de formatos WebP/AVIF (UD6).

    Lighthouse Auditorías automatizadas de rendimiento, accesibilidad y SEO. Introducción a las auditorías técnicas de la UD10 y UD12.

    3. Pruebas de diseño adaptable (Testing Responsive)

    3.1 Device Toolbar

    El panel de emulación permite simular viewports de dispositivos específicos (iPhone, iPad, Pixel) así como ajustar dimensiones personalizadas arrastrando los márgenes de la vista previa.

    Punto de verificación Procedimiento de comprobación
    Desbordamiento horizontal Verificar que no aparezca barra de desplazamiento lateral revisando el ancho de body.
    Legibilidad del texto Confirmar escalas tipográficas legibles manteniendo el zoom del navegador al 100%.
    Áreas táctiles (Touch targets) Asegurar un tamaño mínimo de 44×44px en elementos interactivos mediante la regla de DevTools.
    Imágenes adaptativas Inspeccionar el panel Network (columna Size) para confirmar que <picture> o srcset cargan el archivo óptimo.

    3.2 Limitaciones de la emulación

    Diferencia entre emulación y dispositivo real

    El Device Toolbar simula las dimensiones del viewport, pero no sustituye el motor de renderizado real. Una interfaz probada en la emulación de iPhone dentro de Chrome está utilizando el motor Blink, no el motor WebKit nativo de iOS. Las pruebas en dispositivos o motores reales son imprescindibles.

    4.3 Consultas de soporte en CSS (@supports)

    Las reglas @supports (Feature Queries) permiten aplicar estilos avanzados solo si el navegador soporta dicha propiedad:

    /* Configuración base compatible */
.grid-productos {
  display: flex;
  flex-wrap: wrap;
}

/* Mejora progresiva para navegadores con soporte de Subgrid */
@supports (grid-template-columns: subgrid) {
  .grid-productos {
    display: grid;
    grid-template-columns: subgrid;
  }
}

    4.4 Mejora Progresiva vs. Degradación Elegante

    Estrategia Punto de partida Principio de diseño
    Progressive Enhancement (Recomendado) Estructura funcional básica en HTML/CSS semántico. Se añaden capas de interacción avanzadas según las capacidades del navegador.
    Graceful Degradation Construcción orientada a navegadores de última generación. Se aplican parches y polyfills cuando el código falla en navegadores antiguos.

    Estrategia de Mejora Progresiva

    La Mejora Progresiva constituye la estrategia más sólida en el desarrollo frontend: la base en HTML semántico (UD3) garantiza la usabilidad del contenido independientemente de si los scripts de JavaScript se ejecutan o son bloqueados.

    4.5 Ajustes de navegadores para contenidos multimedia e interactividad (RA4.b)

    Factor de configuración Causa del comportamiento Estrategia de diagnóstico / Solución
    Soporte de códecs Ausencia de decodificación por licencias de software (ej. H.265). Inspeccionar en el panel Network qué elemento <source> es seleccionado.
    Políticas de Autoplay Restricciones de reproducción automática con audio en Chrome/Safari. Confirmar el aviso contextual en la consola de JavaScript y añadir el atributo muted.
    Restricción de JavaScript Extensión de bloqueo de scripts o navegación en modo estricto. Probar la aplicación en modo incógnito desactivando extensiones del usuario.
    Formatos de imagen recientes Incompatibilidad con formatos como AVIF en versiones desactualizadas. Implementar la etiqueta <picture> con fallbacks a WebP o JPEG (UD6).

    5. Ejercicio práctico guiado

    Actividad de consolidación (no evaluable)

    Objetivo: Elaborar una evaluación sistemática del comportamiento de la interfaz en diferentes entornos y resoluciones.

    Pasos recomendados para practicar:

    1. Tabla de compatibilidad: Evalúa el proyecto en al menos 3 navegadores con motores distintos (Blink, Gecko, WebKit) y 3 resoluciones (móvil, tablet, escritorio).
    2. Registro de observaciones: Verifica la correcta renderización visual, el funcionamiento de los eventos de la Sección 8.1 y los formatos entregados por la red (panel Network).
    3. Resolución de discrepancias: Identifica un punto de incompatibilidad y resuélvelo mediante una regla @supports o un recurso de reserva (fallback).
    4. Documentación: Describe brevemente en el archivo README.md del proyecto la estrategia de Mejora Progresiva aplicada.

    6. Resumen del bloque UD8 y conexión posterior

    • El DOM representa la estructura activa del documento, mientras que los eventos gestionan la respuesta interactiva de la interfaz.
    • La delegación de eventos y el diseño de formularios con feedback accesible (aria-invalid) garantizan aplicaciones eficientes y accesibles.
    • Las pruebas de compatibilidad en múltiples motores de renderizado garantizan una experiencia homogénea para todos los usuarios.
