    1. Navegación por teclado

    1.1 Controles e interacción básica por teclado

    Tecla / Combinación Comportamiento esperado en la interfaz
    Tab Avanza el foco hacia el siguiente elemento interactivo.
    Shift + Tab Retrocede el foco hacia el elemento interactivo previo.
    Enter Activa enlaces, botones y confirma el envío de formularios.
    Espacio Alterna el estado de casillas (checkboxes), botones y conmutadores.
    Flechas de dirección Desplaza la selección dentro de componentes agrupados (menús, pestañas, radio buttons).
    Esc Descarta modales, menús desplegables y componentes superpuestos. 
    flowchart TD
    A["Foco inicial"] -->|Tab| B["Enlace 1"]
    B -->|Tab| C["Botón de acción"]
    C -->|Tab| D["Campo de formulario"]
    D -->|Tab| E["Enlace 2"]

    1.2 Gestión del orden mediante el atributo tabindex

    Valor Efecto técnico
    (Sin atributo) Conserva el flujo natural de tabulación según la posición del elemento en el DOM.
    tabindex="0" Añade un elemento no interactivo al flujo natural de navegación por teclado.
    tabindex="-1" Excluye el elemento del flujo de tabulación manual, manteniendo el enfoque programático por JS (.focus()).
    tabindex="1" o mayor ⚠️ Desaconsejado: Altera el orden natural del foco y genera experiencias inconsistentes.

    Uso indebido de tabindex positivo

    El uso de valores positivos (tabindex="1") rompe la navegación lógica del documento. Si el orden de tabulación no coincide con la experiencia visual, la solución técnica consiste en reorganizar la estructura del código HTML, no en alterar los índices de foco.

    1.3 Indicador de foco visible (:focus-visible)

    /* Práctica desaconsejada: elimina el indicador de accesibilidad */
*:focus {
  outline: none;
}

/* Solución recomendada: estilo visible personalizado para teclado */
:focus-visible {
  outline: 3px solid var(--color-brand-primary, #005fcc);
  outline-offset: 2px;
}
    Regla CSS Canal de activación Recomendación de uso
    :focus Se aplica con cualquier método de entrada (clic con ratón, toque o teclado). No utilizar para eliminar bordes de forma global.
    :focus-visible Se activa únicamente cuando el navegador detecta una navegación por teclado. Opción preferida: Evita marcas visuales en clics de ratón manteniéndolas al navegar con teclado.

    1.4 Trampa de foco (Focus Trap) en ventanas modales

    Una ventana modal accesible debe restringir el foco de tabulación dentro del contenedor activo mientras permanece abierta, impidiendo que el usuario navegue accidentalmente por los elementos que se encuentran detrás del fondo.

    flowchart TD
    A["Primer elemento focusable del modal"] -->|Tab| B["Elementos intermedios"]
    B -->|Tab| C["Último elemento focusable del modal"]
    C -->|"Tab - Atrapar foco"| A
    function atraparFoco(modal) {
  const focusables = modal.querySelectorAll('button, [href], input, select, textarea, [tabindex="0"]');
  const primero = focusables[0];
  const ultimo = focusables[focusables.length - 1];

  modal.addEventListener('keydown', (e) => {
    if (e.key !== 'Tab') return;

    if (e.shiftKey && document.activeElement === primero) {
      e.preventDefault();
      ultimo.focus();
    } else if (!e.shiftKey && document.activeElement === ultimo) {
      e.preventDefault();
      primero.focus();
    }
  });
}

    2. Lectores de pantalla y árbol de accesibilidad :material-text-to-speech:

    2.1 Herramientas según el sistema operativo

    Sistema Operativo Lector de pantalla Modalidad
    Windows NVDA Gratuito / Código abierto (Recomendado para pruebas)
    Windows JAWS Licencia comercial (Estándar en entornos corporativos)
    macOS / iOS VoiceOver Integrado nativamente en el sistema
    Android TalkBack Integrado nativamente en el sistema
    ChromeOS ChromeVox Integrado en la plataforma

    Plataformas para la realización de pruebas

    Para completar las actividades del curso se recomienda utilizar NVDA (en entornos Windows) o VoiceOver (en macOS/iOS). No se requiere ningún software bajo licencia comercial para verificar los fundamentos de accesibilidad.

    2.2 El Árbol de Accesibilidad (Accessibility Tree)

    flowchart TD
    A["Lector de pantalla"] --> B["<b>Árbol de Accesibilidad</b><br/>(Accessibility Tree)"]
    B --> C["Construido a partir de:<br/>HTML Semántico + Atributos ARIA"]
    C --> D["Nota: El DOM visual NO equivale<br/>al árbol de accesibilidad"]

    El navegador genera un árbol de accesibilidad independiente a partir del DOM. Las tecnologías asistivas leen esta estructura interna. Si un elemento carece de semántica adecuada en el HTML, no estará disponible para un lector de pantalla aunque se muestre correctamente en pantalla.

    2.3 Verbalización de elementos frecuentes

    Estructura HTML Anuncio procesado por el lector de pantalla
    <img alt="Zapatillas rojas de running"> "Imagen: Zapatillas rojas de running"
    <img alt=""> (Imagen decorativa) (Omitida deliberadamente del árbol de accesibilidad)
    <img> (Sin atributo alt) "Imagen sin descripción" o lectura directa del nombre de archivo.
    <button>Enviar</button> "Enviar, botón"
    <a href="/perfil">Perfil</a> "Perfil, enlace"
    <input type="email" aria-label="Correo electrónico"> "Correo electrónico, edición de texto"

    Diferencia entre alt="" y omitir el atributo alt

    Utilizar alt="" comunica que la imagen es puramente decorativa y debe ser ignorada. Omitir el atributo alt representa un error de maquetación que obliga al lector a interpretar el elemento, anunciando nombres de archivo ambiguos como imagen_v2_final.png.

    3. Verificación del contraste de color

    3.1 Herramientas para la medición de contraste

    Herramienta Entorno Aplicación principal
    WebAIM Contrast Checker Aplicación Web Cálculo explícito del ratio a partir de valores hexadecimales.
    Chrome DevTools Integrada (Elements → Color Picker) Verificación del ratio en tiempo real con indicador de cumplimiento A / AA / AAA.
    Stark Plugin para Figma / Sketch Verificación de contraste en la fase previa de diseño (UD1). 
    flowchart TD
    A["Color de texto<br/>(#333333)"] --> C["Calcular ratio de contraste<br/>respecto al fondo"]
    B["Color de fondo<br/>(#FFFFFF)"] --> C
    C --> D{"¿Ratio ≥ 4.5:1?"}
    D -->|Sí| OK["<b>Cumple Nivel AA</b><br/>(Texto de tamaño estándar)"]
    D -->|No| FAIL["<b>No cumple</b><br/>Ajustar luminosidad de texto o fondo"]

    3.2 Patrones habituales de deficiencia de contraste

    Escenario de diseño Causa de la deficiencia Solución técnica
    Texto gris sobre fondo blanco (#AAAAAA sobre #FFFFFF). Genera un ratio aproximado de ~2.3:1 (inferior al mínimo de 4.5:1). Oscurecer el tono del texto hasta alcanzar la proporción requerida.
    Textos de ayuda (placeholders) en inputs. Los navegadores aplican opacidades reducidas por defecto. Personalizar la pseudo-clase ::placeholder asegurando ratio adecuado.
    Texto sobre imágenes de fondo heterogéneas. La variabilidad de zonas claras y oscuras impide garantizar el contraste. Incorporar una capa superpuesta (overlay) o un fondo sólido detrás del texto.

    4. Ejercicio práctico guiado

    Actividad de consolidación (no evaluable)

    Objetivo: Evaluar la usabilidad y accesibilidad de la interfaz mediante técnicas manuales de navegación por teclado, uso de lector de pantalla y medición de contraste.

    Pasos recomendados para practicar:

    1. Prueba de navegación por teclado: Recorre la aplicación completa utilizando exclusivamente la tecla Tab y combinaciones de interacción. Identifica bloqueos de foco o componentes inaccesibles.
    2. Verificación de foco: Confirma que el indicador visual :focus-visible resulte claro en todos los elementos enfocables.
    3. Evaluación con lector de pantalla: Activa NVDA o VoiceOver y navega por la página principal. Comprueba el anuncio de imágenes, botones, modales y enlaces.
    4. Corrección de hallazgos: Soluciona las incidencias identificadas (atributos alt ausentes, pérdida de foco, inconsistencias de tabulación).
    5. Auditoría de contraste: Selecciona 5 combinaciones principales de texto/fondo y verifica sus ratios mediante WebAIM Contrast Checker o Chrome DevTools.

    5. Cierre de la unidad y conexión posterior

    • El árbol de accesibilidad procesa la información semántica del proyecto, haciendo indispensable el uso de etiquetas apropiadas (UD3).
    • La navegación por teclado constituye el mecanismo de acceso principal para múltiples tecnologías asistivas.
    • Cubiertos los fundamentos teóricos (Sección 9.1) y la evaluación manual (Sección 9.2), la UD10 abordará la automatización del proceso mediante herramientas de auditoría profesional (Lighthouse, axe-core).
