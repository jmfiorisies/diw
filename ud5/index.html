    1. El problema que resuelve una arquitectura CSS

    Sin convenciones ni arquitecturas definidas, un proyecto de código CSS de tamaño medio suele derivar en problemas de escalabilidad:

    flowchart TD
    subgraph Problemas ["Caos a Escala en CSS Tradicional"]
        A[".card { ... }"] --> P1["<b>Incertidumbre:</b> ¿Se puede reutilizar sin romper la maquetación en otro contexto?"]
        B[".btn-2 { ... }"] --> P2["<b>Nomenclatura deficiente:</b> Nombres sin significado semántico ni contexto."]
        C[".card .btn:hover { ... }"] --> P3["<b>Alta especificidad:</b> Selectores anidados difíciles de sobrescribir."]
    end

    Dos filosofías dominan la industria actual para solucionar este problema: BEM (nomenclatura estructurada) y Utility-First (clases atómicas combinables popularizadas por Tailwind CSS).

    flowchart TD
    A["<b>CSS sin Convención</b><br/>(Dificultad de mantenimiento)"] --> B["<b>BEM</b><br/>(Semántica + Estructura de componentes)"]
    A --> C["<b>Utility-First</b><br/>(Composición atómica + Velocidad)"]

    B --> D["<b>UD7: Design Systems</b><br/>Implementación en código (Storybook)"]
    C --> D

    2. BEM (Block, Element, Modifier)

    2.1 La sintaxis

    .bloque {}
.bloque__elemento {}
.bloque--modificador {}
.bloque__elemento--modificador {}
    Parte Qué representa Ejemplo
    Block (Bloque) Componente independiente con significado propio .card
    Element (Elemento) Parte interna ligada al bloque, sin sentido fuera de él .card__title, .card__image
    Modifier (Modificador) Variación de estado, aspecto visual o comportamiento .card--featured, .card__button--disabled

    2.2 Ejemplo de implementación

    <article class="card card--featured">
  <img class="card__image" src="producto.jpg" alt="Zapatillas running">
  <h3 class="card__title">Zapatillas Running Pro</h3>
  <p class="card__price">79,99 €</p>
  <button class="card__button card__button--primary">Añadir al carrito</button>
</article>

    .card { 
  display: flex; 
  flex-direction: column; 
  gap: 8px; 
}

.card--featured { 
  border: 2px solid var(--color-brand-primary); 
}

.card__title { 
  font-size: 1.25rem; 
}

.card__button--primary { 
  background-color: var(--color-brand-primary); 
}

    Plana especificidad con BEM

    Con BEM, la especificidad de todas las clases se mantiene fija en (0, 0, 1, 0) (una sola clase). Se evita por completo el anidamiento inútil (.card .title) y el uso de !important, puesto que la propia clase encapsula el contexto.

    2.3 Ventajas y límites de BEM

    Ventaja técnica Límite de uso
    Nombres autoexplicativos que comunican estructura en el HTML Nombres de clases extensos (card__button--primary)
    Especificidad plana y predecible Requiere disciplina y acuerdo por parte del equipo
    Encaja con la metodología Atomic Design (UD7) No resuelve la reutilización de valores (colores/espaciados) por sí solo — requiere Design Tokens (UD2)

    3. Utility-First con Tailwind CSS

    3.1 Cambio de paradigma

    Enfoque BEM Enfoque Utility-First (Tailwind)
    Escribes CSS una vez, asignas un nombre semántico y lo reutilizas Compones la interfaz combinando clases atómicas existentes sin escribir CSS nuevo
    HTML limpio; el CSS contiene la lógica de diseño El HTML describe la lógica visual; el archivo CSS se mantiene mínimo 
    <!-- Mismo componente Card maquetado con clases Utility de Tailwind CSS -->
<article class="flex flex-col gap-2 border-2 border-blue-600 rounded-lg p-4">
  <img class="rounded-md" src="producto.jpg" alt="Zapatillas running">
  <h3 class="text-xl font-semibold">Zapatillas Running Pro</h3>
  <p class="text-gray-600">79,99 €</p>
  <button class="bg-blue-600 text-white rounded-md px-4 py-2">
    Añadir al carrito
  </button>
</article>

    3.2 Tabla de equivalencias CSS ↔ Tailwind CSS

    Propiedad CSS pura Clase Utility equivalente
    display: flex; flex
    flex-direction: column; flex-col
    gap: 8px; gap-2
    padding: 16px; p-4
    border-radius: 8px; rounded-lg
    background-color: #2563eb; bg-blue-600
    @media (min-width: 768px) { ... } Prefijo md: (ej. md:flex-row)

    3.3 ¿Cuándo elegir BEM y cuándo Tailwind CSS?

    flowchart TD
    Q1{"¿El proyecto cuenta con un<br/>Design System con tokens bien definidos?"}

    Q1 -->|Sí, priorizamos velocidad de desarrollo| TW["<b>Tailwind CSS</b><br/>(tailwind.config.js mapea los tokens de diseño)"]
    Q1 -->|No, requerimos semántica estricta en HTML| BEM["<b>Metodología BEM</b><br/>(Arquitectura CSS tradicional organizada)"]
    Q1 -->|Proyecto complejo de gran escala| BOTH["<b>Combinación Híbrida</b><br/>BEM para la estructura del componente + Utilities para ajustes puntuales"]

    Tailwind CSS no reemplaza a los Design Tokens

    Tailwind CSS no sustituye a los tokens de diseño de la UD2: los implementa. El archivo de configuración tailwind.config.js es donde se mapea la paleta de color (brand-primary), las escalas de espaciado y las tipografías para garantizar que coincidan con la especificación de diseño de Figma.

    // tailwind.config.js — Mapeo directo de tokens creados en la UD2
module.exports = {
  theme: {
    extend: {
      colors: {
        'brand-primary': '#1E88E5', // Corresponde al token color.brand.primary
      },
      spacing: {
        'md': '16px', // Corresponde al token space.md
      },
    },
  },
};

    4. Herramientas de validación (RA2.h)

    Herramienta Función de validación Momento de ejecución
    W3C CSS Validator Valida la sintaxis CSS conforme al estándar oficial Evaluación manual y puntual
    Stylelint Linter de sintaxis y reglas de equipo (orden de propiedades, patrón BEM, duplicados) Integrado en el IDE / Canal de CI/CD
    Prettier Formateador automático de código (indentación y comillas) Automático al guardar el archivo 
    flowchart TD
    A["Escribe código CSS"] --> B["<b>Stylelint</b><br/>(Comprobación de reglas y sintaxis)"]
    B --> C{"¿Existen errores de linter?"}
    C -->|Sí| D["Corregir fallos identificados antes de commit"]
    C -->|No| E["Commit / Pipeline de CI validado en verde"]

    Ejemplo de configuración de Stylelint en un archivo .stylelintrc.json para verificar el cumplimiento del patrón BEM:

    {
  "extends": "stylelint-config-standard",
  "rules": {
    "selector-class-pattern": "^[a-z]([a-z0-9-]+)?(__([a-z0-9]+-?)+)?(--([a-z0-9]+-?)+)?$"
  }
}

    5. Actualización de la guía de estilo (RA2.i)

    La guía de estilo creada durante la fase de diseño (UD2 en Figma) debe mantenerse sincronizada con la base de código del proyecto:

    Elemento de Diseño Ubicación en la Base de Código
    Paleta de Colores tailwind.config.js o variables CSS en :root { --color... }
    Escala Tipográfica Clases de utilidad (text-xl) o variables CSS
    Sistema de Espaciado Objeto theme.spacing en Tailwind CSS o variables --space-*
    Catálogo de Componentes Se documenta de forma aislada mediante Storybook en la UD7

    Sincronización del Design System

    El criterio RA2.i requiere actualizar la guía de estilo para garantizar que cada componente nuevo o token ajustado en Figma se refleje en la hoja de estilos del proyecto, evitando divergencias entre diseño y desarrollo.

    6. Ejercicio práctico guiado

    Actividad de consolidación (no evaluable)

    Objetivo: Aplicar una arquitectura CSS profesional (BEM y Tailwind CSS) sobre el código desarrollado en las unidades previas.

    Pasos recomendados para practicar:

    1. Refactor con BEM: Reestructura las clases del componente de tarjeta de producto siguiendo de forma estricta el patrón bloque__elemento--modificador.
    2. Maquetación con Tailwind CSS: Genera una versión alternativa del mismo componente utilizando clases Utility de Tailwind CSS sin alterar el resultado visual final.
    3. Configuración de Tokens: Define un archivo tailwind.config.js que extienda el tema con al menos 4 colores y 3 espaciados procedentes de los tokens de la UD2.
    4. Integración de Stylelint: Configura el linter con la regla de validación del patrón BEM y corrige cualquier discrepancia.
    5. Documentación: Elabora una nota breve en README.md comparando el uso de BEM frente a Tailwind CSS según el contexto del proyecto.

    7. Resumen y conexión con la siguiente unidad

    • BEM proporciona claridad semántica y especificidad plana; Tailwind CSS aporta velocidad y componibilidad.
    • La validación automatizada con Stylelint asegura la coherencia del CSS sin depender del control manual.
    • Con los RA1 y RA2 finalizados, concluye el Bloque I de maquetación y diseño de interfaz. En la UD6 iniciaremos el RA3, abordando la preparación y optimización de recursos multimedia para la Web (WebP, AVIF, SVG y rendimiento).
